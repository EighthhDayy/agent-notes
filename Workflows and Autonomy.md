# Orchestration Patterns: Workflows and Autonomy

Orchestration patterns define how the "context and tools" layer of the Harness is organized—they determine how context flows between LLM calls, how tools are scheduled, and whether the Agent's execution path is predefined or dynamically generated. The orchestration of Agent systems has evolved from simple to complex, with each pattern having its applicable scenarios and corresponding trade-offs. According to Anthropic's experience working with dozens of teams to build LLM Agents, the most successful implementations often do not use complex frameworks, but instead adopt simple, composable patterns.

When building LLM applications, the principle of "from simple to complex" should be followed: first consider a single LLM call. If the problem can be solved by optimizing prompts and in-context examples, there is no need to introduce an Agent system. When multi-step processing is required, consider using workflows for scenarios that can be clearly decomposed into fixed subtasks. Only use autonomous Agents when dynamic decision-making and flexible execution paths are required. It is important to remember that Agent systems typically trade latency and cost for better task performance, and whether this trade-off is worthwhile should be carefully evaluated.

A common counterexample is building a highly complex workflow or multi-Agent system from the very beginning. For example, when designing an Agent to "extract personal memories from millions of chat records," some AI models can easily and quickly produce a seemingly rigorous pipeline: first segment conversations, then arrange Agents for extraction, evidence verification, identity resolution, memory organization, and merging and review, and finally establish a fact graph, a coverage ledger, and immutable versions. Each component makes sense individually, but when combined, they become highly inefficient and unreliable. Because complex workflows have fixed execution topologies, the system tends to add more nodes when encountering new exceptions, making the architecture increasingly complex while reducing its generality. Semantic judgments that the model could originally make based on context instead become hard-coded into the workflow.

Therefore, **the importance of the Harness does not mean that a more complex Harness is better.** The official Manus website summarizes this trade-off as "Less structure, more intelligence." First, provide a sufficiently capable Agent with clear objectives, necessary context, and composable tools, and use natural language to tell it how to investigate facts, compare information, and resolve conflicts like a human. The program only enforces boundaries that must always hold, such as permissions, prohibiting the overwriting of original materials, and atomic publishing. Only when business constraints require it, or evaluations repeatedly expose certain consistent failures, should the corresponding steps be upgraded to dedicated validators, independent Agents, or deterministic processes. Good structure does not anticipate all reasoning on behalf of the Agent, but instead maintains boundaries and returns the decision-making space within those boundaries to the model.
